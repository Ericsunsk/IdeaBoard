## Dependency Direction

- `cmd` stays lightweight and delegates process wiring to `internal/runtime/composition`.
- `internal/runtime` is a Platform Runtime Context using DDD + Clean Architecture: `domain` owns explicit lifecycle state and invariants, `application` coordinates lifecycle transitions and draining budgets, and `composition` is the sole assembly root.
- Runtime interfaces (`interfaces/http`, `interfaces/worker`) and adapters (`adapters/*`) stay isolated; business contexts must never depend on `internal/runtime`.
- Business contexts may depend on `internal/platform` and `internal/db/sqlc` through their own repositories or adapters.
- `internal/platform` must not import business contexts.
- `internal/tasking` may contain multiple focused packages because Tasking covers model, submission, queueing, persistence, statistics, media validation and lifecycle state.
- **Identity Shared Kernel.** `internal/identity/principal`, `internal/identity/trust`, and `internal/identity/authidentity` are a shared kernel consumed by AI Gateway, Prompts, Credits, Rewards, Search Catalog, and Runtime HTTP. They are listed here on purpose: these directories are deliberately _not_ enumerated per consuming context, so do not "fix" the Contexts table by removing or relocating them. `principal` carries the authenticated subject plus its capability set and is the single authorization vocabulary every handler reads; `trust` and `authidentity` carry the verified-identity vocabulary provisioning depends on. Adding a new principal concept means extending `principal`, never re-deriving subject or capability shape inside a consumer.
- **Media Shared Kernel.** `internal/media/workspacemedia`, `internal/media/errors`, and `internal/media/ingestion` expose Media-owned contracts shared with Tasking, Library, and Runtime. `workspacemedia` defines Upload Session, Media Asset, Task Asset, and their store ports; `errors` defines media error codes; `ingestion` defines storage-ingestion types consumed through `storage/ports`. Sharing these contracts does not transfer ownership of Media facts to consumers.

| Business User             | The platform user profile and business lifecycle linked to an Auth Identity; owned by Identity.                                                |
| Principal                 | The authenticated subject and capabilities established for the current request.                                                                |

| Membership Role           | A user's role within a particular Workspace or Organization; distinct from the platform Admin role.                                            |
| Billing Account | Stable funds identity holding the unified balance: one Personal account per user and one shared account per Organization (see [ADR-0038](../../docs/adr/0038-personal-organization-billing-model.md)); Workspace records consumption location and User the actual operator. No independent Workspace accounts, no link rows, no payer switch. |
| Billing Account Wallet    | One Wallet per stable Billing Account holding the unified balance; canonical accounting terms belong to [Credits](./internal/credits/CONTEXT.md). Workspace records the consumption location, User the actual operator. |
| Service                   | An executable AI image capability; Workflow defines its contract, Generation selects its Model, Billing prices it, and Tasking runs its Tasks. |
| Library Asset             | A saved library reference discriminated by source (external provider reference or managed Media save), owned by Library. Media display dimensions project from Media at read time; task lineage is provenance only. |
| Upload Session            | Coordination of one image upload through transfer, completion, failure, or expiry; not the resulting Media Asset.                              |
| Media Asset               | A managed image identity within a Workspace, with validated original-image facts and an independent lifecycle.                                 |

Qualify overloaded terms with their context: Auth Session, Upload Session, Checkout Session, Board Session; Library Asset or Media Asset; Workspace Billing Account or Credit Account. Use `Service` for the product capability, not a Provider Model or a running server process.

Workflow uses `feature` in its registry and Feature Prompt names; the shared product capability is the same Service, not a second catalog. Generation as a context owns routing for all image Services; the `generation` Service is one capability within that set.

## Current Design Rules

- Managed image ingestion is owned by Media: Library materialization and Task results share byte validation, checksum verification, upload-session completion, and bounded failure cleanup. Source policies, replay, output provenance, and Task settlement remain caller-owned.
- Workspace deletion refuses pending/running Tasks under the Workspace row lock; canonical Task completion/cancellation must settle their Credit Holds before deletion. The Workspace FK lock serializes concurrent submissions with deletion.
- Task submission is transactional: insert the business task and enqueue the River job in the same PostgreSQL transaction.
- Board access requires current Workspace membership, including for the creator. Board mutations read actor and grant-target membership inside the accepting transaction, locking the Workspace before Board rows. Workspace departure deletes membership and direct Board grants, advances affected access versions, and records directed access outbox facts in one transaction.
- Board document acceptance authorizes all Media references through the Media policy inside the same transaction that writes the revision and durable references. Newly supplied references cannot authorize themselves.
- Canvas task submissions bind to their Board (`board_id` + submit-time `access_version` in the `workflow_input` envelope, same settlement transaction): Board identity and generate capability are validated before Quote/Hold, omitted Board IDs stay non-Canvas tasks with their own workspace permission (submitter-only reads, never auto-published). Task reads/cancel/progress delivery are submitter- or current-Board-reader-only; completions auto-publish to Quick Saves only for currently team-shared Boards (re-judged at completion, so stale callbacks after unshare never publish); manual Library saves of restricted material require owner standing (creator/Manager) plus usage rights. Prompts/params stay write-only; billing records carry billing facts only.
- Canonical Task media uses ordered `AssetID + role` facts. Submit atomically creates `task_input` refs, every terminal transition releases them, reclamation protects them while active, and runtime resolves each Workspace Media Asset through the fixed `builtin-local` profile into provider-only URLs; persisted Task Params never contain media URLs.
- S3-compatible credentials are control-plane only: upload, capability checks, listing, and deletion use the configured Endpoint; stored-object reads use the immutable Storage Profile `access_domain` delivery plane through `safehttp`, for storage reads and provider delivery. Browser display renditions are same-origin API bytes from the Media renderer, not direct storage URLs.
- Task submission idempotency uses `client_action_id` as the user-action boundary: retries of the same user action return the existing Task, while intentional reruns send a new `client_action_id`.
- River + PostgreSQL are the task queue and task state fact source.
- River redelivery recovers an interrupted `running` task by reusing its execution token to reacquire the lease; a different token remains fenced out, and no startup reaper is active.
- NATS JetStream is an event layer for task status, audit and realtime fanout; it is not a task queue.
- Worker concurrency reads only the deploy-level `RIVER_WORKER_CONCURRENCY`; retry/timeout policy is owned by the Platform `riverpolicy` module, NATS retention is fixed at 7 days by the Events implementation. Database pool sizing is hardcoded (`DefaultPoolMaxOpenConns`/`DefaultRiverPoolMaxConns`, budget enforced by `Config.Validate`); per-queue River `MaxAttempts` live in `riverpolicy.RiverRetryMatrix` as the single source of truth and every queue reports its own depth/lag gauges. Process role is deploy-level too (`API_MODE=all|http-only|worker-only`, ADR-0021): http-only serves API/SSE and only enqueues (no workers, no periodic schedules), worker-only consumes every matrix queue with no HTTP listeners, and periodic schedules run only where workers run.
- Admin only manages the typed `OutboundPolicySetting`. The egress allowlist is read from DB before every outbound operation, takes effect dynamically, and fails closed on read errors; writes must update `system_configs` and the append-only actor audit in the same PostgreSQL transaction.
- Worker implementation stays in `internal/runtime/interfaces/worker` as the Runtime execution adapter. Its implementation is split into isolated subpackages (`providers`, `river`, `billing`, `visionbilling`, `outbox`); `providers` decouples strictly through `runtime/ports`, while subpackage boundaries are enforced by architecture tests. Workspace task execution lives in `internal/tasking/interfaces/worker`.
- Workflow owns executable feature contracts; Feature Prompt configuration only owns the current prompt template and is updated in place without version or revision history. Billing availability and Service Model Pool routing must both gate submission before Hold. Quote (task-quotes and billing-quotes for ai-image SKUs), readiness preflight, and submit share one `RoutingResolver` availability decision (`422 service_resolution_unavailable`); submit resolves and pins the routing snapshot atomically with Credit Hold, task insert, and River enqueue. Omitted resolutions are normalized to the Service policy's canonical `1k`/`2k`/`4k` value; `params.output_resolution` is the client source of truth and the top-level billing resolution must agree with it exactly. Only `1k`, `2k`, and `4k` are accepted; `default` is not a request or billing variant.
- `tasks.result` may hold a durable result envelope. Successful image tasks keep top-level `image_url`/`image_urls` for Canvas compatibility; workflow-specific parse failures may store `parsed_output_status`, `parsed_output` and a bounded `raw_provider_output_preview` so Admin/Canvas can diagnose retry or failed states without treating them as successful outputs.
- Unless schema or query contracts change, do not edit migrations or generated sqlc code.
- Credits Ledger shares PostgreSQL with Tasking; other contexts may only write ledger state through `credits.Commands`, never by touching balance projections or the Ledger directly.
- Rewards shares a caller-owned PostgreSQL transaction with Credits; Rewards only Grants through `credits.Service.InTx`, never writing the Ledger or balance projections directly.
- Rewards Redeem uses an endpoint-private per-user in-process limiter with a current/previous HMAC registry; startup must reject a missing current key, or removal of a previous key still referenced by any persisted RewardCode. This abuse control does not enter Platform interfaces or database schema.
- Billing selects an immutable price version by SKU and Output Resolution and generates a Quote; it neither selects a Model nor writes the Credits Ledger. Task readiness and submission additionally require Generation routing availability.
- Credit Commands that must commit atomically with caller business state use caller-owned pgx transactions via `credits.Service.InTx(pgx.Tx)` or transaction-scoped `credits.CommandsInTx(pgx.Tx)`; both invoke the same typed Credit Command, the caller owns commit/rollback, and no double writes from outside.
- Canonical AI Image Workflow Submit completes Quote/Hold/snapshot/Task/River in one pgx transaction inside Tasking, holding the Workspace's stable Billing Account with the submitter as operator (quote/readiness preflights resolve the same account and enforce the same Board-edit and funds eligibility); terminal transition updates Task facts in one pgx transaction in the Task Store, and atomically Captures/Releases through the same transaction-scoped `workspacetasks.Service.Complete`/`Fail`/`Cancel` path converging on the submit-time row facts. The Task Store holds no application-lifetime Billing dependency. Pure local edit operations stay outside this billing boundary.
- Task Billing settlement uses a typed `free | held | captured | released` state machine: `0 Ideas` Quotes enter `free` directly; paid tasks converge idempotently from `held` to `captured` or `released` only, never backwards or across terminal states.
- A River drawing job whose final execution fails while terminal convergence is temporarily unwritable persists a settlement-only marker and snoozes; retries after restart only run terminal convergence and never call the Provider again. If the marker record itself fails, a dedicated settlement-only River job is enqueued as durable fallback.
- Identity user lifecycle provisions/freezes Wallets and claims the Welcome Grant atomically through the typed `credits.WalletLifecycle` seam; Ledger writes and runtime privilege stay exclusively with Credits.
- Wallet lifecycle status and reasoned Restrictions are independent; `credits.WalletRestrictionCommands` is the sole Restriction write seam. New Grants/Deductions/Holds require both active lifecycle and no active Restriction; existing Holds must keep converging on Capture/Release, and authenticated Admin linked Refunds/Corrections stay available for repair, while Wallets start no new consumption.
- Reconciliation high-risk open Findings isolate consumption by binding the Finding's Ledger Integrity Restriction; confirmed-resolved scans, high→low transitions, or Wallet ownership changes release only the matching Restriction without touching Wallet lifecycle status.
- Reconciliation Runs distinguish manual/scheduled Triggers; Stale Hold is fixed at 24 hours and lives only as DB-internal per-Run snapshots, never entering Admin requests or public Run DTOs. River PeriodicJobs schedule the daily ScheduleJob at 03:00 Asia/Shanghai and use a catch-up ScheduleJob at leader start when no successful Run exists for over 24 hours; ScheduleJobs only call the Credits-internal transaction-bound start seam, snooze when another active Run exists, and failed target slots past due reuse the original Run with terminal fields cleared for re-enqueue.
- Admin Credit Health is Reconciliation's current Read Model: it composes the active Run, latest successful/failed Runs, open Finding aggregates, and exact Ledger Integrity Restriction Wallet counts inside one repeatable-read snapshot; an active Run never overrides the last trusted result, and no successful check for over 48 hours reads as stale.
- User deletion uses `user_deletion_requests` as durable state: freeze the business user and Wallet first, then idempotently converge Auth → Storage → tombstone phases; cross-service failures must never reactivate an active Wallet.
- Usage range is typed `7d | 30d | 1y`, mapping to 7 / 30 / 365 `Asia/Shanghai` daily buckets including today; range filters Trend only, Lifetime stays unchanged.
- `CaptureUsageReader` and `LogicalTaskUsageReader` are **consumer-owned**: Usage declares the interfaces it needs (`internal/usage/application/service.go`) and Credits/Tasking supply them. Credits supplies the immutable `UsageFilter` value; Usage owns the reader interfaces and composes Credits and Tasking facts without accessing their persistence.
- Usage composes immutable Credit Captures with Task Billing snapshots in realtime, using a feature-local, capacity-2,048, ~30s TTL per-process LRU cache. Financial managers read account usage, Workspace managers read their Workspace, and other members read their own account usage. The cache must isolate by `(billing_account_id, workspace_id, actor_user_id, range)` with copy-on-read/write; multi-instance deployments accept ~30s eventual freshness with no Redis invalidation or Daily Projection.
- Billing Records composes Credits Ledger with immutable Task Billing Snapshots read-only: it uses authenticated `user_id` with Ledger sequence keyset pagination, hides internal or not-yet-displayed flows like Hold/Release/Refund, emits stable backend `kind/title`, and the frontend must not parse Ledger `source/reason`.
- New routes render through the contract kernel: errors use `contract.Code` (callers branch on code, never message text; `StatusOf` owns the code-to-status mapping) with the single envelope (`contract.RenderSuccess` / `RenderCreated` / `RenderAccepted` / `RenderPaginated` for 2xx JSON, `contract.RenderError` / `RenderCode` for errors). The specs mirror this: 2xx JSON bodies are `{data, meta?}` (`meta` required on pages), errors are `ErrorEnvelope` / `ControlErrorEnvelope`, every response carries `Request-Id`. Frozen exceptions only: binary image responses (original content, rendered display tiers, public avatar/logo, and control brand-logo SVG) and SSE streams (workspace events, user notification hints, control monitor) — never JSON outside the envelope.
- HTTP envelopes are three layers, and `platform/response` is not deprecated. Layer 1 is `response.*` (numeric `{code,msg,message_safe}` successes plus `MachineError` `{code,msg,message_safe}`) as the control-proxy translator input: legacy domain handlers keep rendering it, and the Control Plane translates it at the boundary (pinned by `TestControlProxy*` in `internal/runtime/interfaces/http/control/proxy_envelope_test.go`). Layer 2 is the wire-stable machine envelope `{code,msg,message_safe}` edge tables (per-domain sentinel→code tables declared as `errorrender.Mapping` and rendered via `errorrender.RenderMapped`, rewards admin/redeem partitioned by `Scope`), frozen per the kernel code registry in `internal/platform/contract`. Layer 3 is the blessed protocol exceptions that are never JSON envelopes (health/readiness probes, Stripe webhook bytes, SSE streams, cross-cutting middleware), pinned by `TestContractInventory*` in `internal/runtime/interfaces/http/contract_inventory_test.go`. New v1/control JSON handlers render via `platform/contract`; only the documented exceptions live outside it (pinned by `TestContractV1EnvelopeUnification` / `TestContractControlEnvelopeUnification`).
- Public feeds page with opaque cursor + `page_size` (`contract.ParsePageSize`: default 20, max 100; v1 handlers parse it only through the `v1PageSize` gin helper; cursors come from `contract.EncodeCursor`, stay bound to principal/filters/sort, malformed input renders `pagination_cursor_invalid`). Admin/control lists bound size with `contract.ParseLimit` (`limit`, default 50, max 200, the single home for the legacy limit dialect) plus an opaque `cursor`, or store-ordered `before_id` (`contract.ParseBeforeID`) where the backing store is id-ordered (reconciliation runs/findings, reward redemptions). The search edge validates `limit` through `contract.ParseSearchLimit` (24/48) and rewards edges through `contract.ParseRewardLimit` (20/100). `workspacemedia.ListAssets` keeps its `(limit, offset)` signature, but the offset is always a decoded `AssetCursor` position (see `cursor.go` for the `ListAssetsByCursor` migration plan). Never add `page` / `page_number` offsets or raw (non-opaque) cursors.
- `Idempotency-Key` is header-only (no body key): required on ledger-writing creates (checkout sessions, credit grants/deductions/refunds/corrections, task submit, reward redemption, payment refunds) and on every control mutation; optional on naturally-idempotent writes (renames, role updates, idempotent restores/revokes, read-like POSTs such as quotes, batch reads, search, route-preview) — but every mutation documents its status in the spec (the shared `IdempotencyKey` parameter when required, else an explicit `No Idempotency-Key …` description). Key reuse with the same request hash replays the first result; reuse with a different hash renders 409 `*_idempotency_conflict`.
- New ID scalar patterns must match the kernel alphabet `^<prefix>_[A-Za-z0-9_-]+$` (`contract.IsValidPublicID`) and pin the family in the `scripts/openapi-pattern-check.sh` canonical table. Reserved prefixes (`ba_`, `lmat_`, `rwd_`, `rdm_`, `rec_`) stay off the wire until their `public_id` columns land; rewards/reconciliation ids remain numeric by formal exception.
- Structural spec guard: `scripts/openapi-pattern-check.sh` asserts every operation has an `operationId` and every mutation (`POST`/`PUT`/`PATCH`/`DELETE`) states its Idempotency-Key status. Grandfathered gaps live in that script's allowlist; current spec-side residuals are report-only (fix via spec PR, never silently).

Deliberately NOT converged (context-specific, different code/state/scope — do not "fix" these):

- `未配置` vs `暂不可用` vs `不存在` (different states: never configured, transiently down, missing entity).
- `认证服务拒绝伪装登录` (`Rejected`/`Forbidden`) vs `认证服务伪装登录失败` (`Unavailable`): different codes.
- `不能操作…` (admin self-operation guard) vs `不能模拟…` (impersonation): different semantics.
- `需要管理员权限` (admin-required) vs `权限不足` (generic forbidden): different nuance.
- `*不存在` / `*失败` / `*不能为空` / `*无效` with different subjects: entity-specific, keep the subject.
- `社区模型目录*` (detect/fetch operation) vs `models.dev *` (reference-load operation): different operations.
- Suffix-shared but cause-specific strings (`请联系管理员`, `请检查配置或稍后重试`, `请稍后重试` with different verbs/subjects).

## When To Expand A Context

Create or expand a backend context only when at least one condition is true:

- A domain area has multiple packages whose names become clearer when grouped.
- Callers need to understand sequencing, status transitions, persistence rules or error handling that should live behind a smaller module interface.
- Testing a business workflow requires assembling too many low-level collaborators.
- A group of packages already shares stable domain language that is clearer than technical-layer naming.

If none of these apply, keep the current package location and improve the local module interface directly.
