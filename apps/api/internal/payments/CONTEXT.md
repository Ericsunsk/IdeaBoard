# Payments Context

Payments owns Stripe configuration, signed Webhook intake, and the payment lifecycle (orders, checkout, refunds, disputes, reconciliation).
It does not own platform Idea balances or the ledger; Wallet, the double-entry Ledger, balance projections, and all Credit writes stay exclusively with Credits.

## Domain Language

| Term                         | Meaning                                                                                                                                                                               |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Current Stripe Configuration | Currently effective Stripe Credential Generation, Product Tax Code, and purchase switch; publishing runs only a short transaction                                                     |
| Stripe Credential Generation | Immutable Stripe account, encrypted Secret, Payment Method Configuration, and provider resource references; each Payment Order permanently references the generation used at creation |
| Stripe Gateway               | Adapter seam through which Payments calls the Stripe API; domain services never depend on Stripe SDK types                                                                            |
| Webhook Inbox                | Minimal receipt fact deduplicated globally by Stripe Event ID; stores only routing and processing metadata, never the raw payload                                                     |
| Ignored Event                | Validly signed event that Payments does not recognize; recorded as `ignored` and acknowledged successfully with no business state change                                              |
| Payment Admin Action         | Append-only audit of Stripe configuration operations, including actor, outcome, and redacted error summary                                                                            |
| Payment Order                | A payer Billing Account's durable intent to buy Ideas and the resulting external-payment facts; distinct from a Task or a Credit Ledger Transaction. The order persists the payer (`billing_account_id`) and the real operator (`user_id`) independently (ADR-0029). |
| Checkout Return              | UI navigation signal from the Stripe browser return; the server must re-read the Stripe Checkout Session, and only a paid canonical Stripe fact may credit                            |
| Purchase Credit              | Credit issuance owed for a verified external payment, distinct from a discretionary Grant.                                                                                            |
| Payment Reconciliation       | Recovery of unresolved external-payment facts against Stripe; distinct from a Credit Ledger consistency check.                                                                        |
| Reconciliation Claim         | One-to-one Payment Order recovery state; token plus generation fence guards a short lease, and Stripe I/O always happens outside the claim transaction                                |
| Payment Refund               | Durable refund fact initiated by Admin or the Stripe Dashboard; locally reserves unconsumed Ideas first on the order's fixed payer Billing Account, then idempotently settles or releases by canonical Stripe status |
| Purchase Refund Hold         | Standalone Credits typed Command reserving unconsumed Ideas from User Available to User Reserved on the order's fixed payer account; it is not spending and may run under an active Restriction                          |
| Purchase Refund              | Return of reserved, unconsumed Ideas to System Issuance for a verified external refund on the order's fixed payer account, distinct from a Credits Refund.                                                               |

## Public Seams

- `Service.GetStripeConfiguration` returns only the safely displayable configuration summary, never API Key, Webhook Secret, or ciphertext.
- `Service.ConfigureStripe` prepares and validates the Stripe account, Product, and Webhook endpoint via `StripeGateway` on enable or change, then atomically publishes the active generation, settings, and success audit in a compare-and-swap short transaction; keeps the old configuration on prepare failure or concurrent publish conflict.
- `Service` purchase-switch off (`purchases_enabled` true to false) commits only a local fast path plus a durable Checkout shutdown run in the same transaction; River expires remaining Sessions idempotently by database cutoff, and periodic recovery resumes enqueueing after process faults.
- `Service.ReceiveStripeWebhook` verifies the raw-body signature, deduplicates, and writes the minimal Webhook Inbox; the later payment-order, refund, and dispute lifecycles stay inside the Payments context.
- `Service.GetPurchaseOptions`, `CreateCheckout`, `ListPendingOrders`, `ContinuePendingOrder`, `AbandonPendingOrder`, `GetPaymentOrderReturnStatus`, `ListRecharges` form the user top-up boundary; every method scopes to the payer Billing Account (the int64 is the account, never the operator), `ListRecharges` keeps credited, refunded, and user-abandoned order facts of that account, and HTTP handlers resolve the workspace's stable account plus Billing Owner/Admin first. The recharge page names its explicit target account.
- `application/hints.Publisher` owns the shared audience policy for Order, Refund, Webhook, and Reconciliation hints through `ports.PaymentHintPublisher`; it resolves current financial managers from the persisted payer, validates and deduplicates recipient IDs, and falls back only to a valid operator when the audience is unavailable. Workflows retain payload facts and post-commit timing; Refund clears the completed ambient transaction before resolving its post-commit audience.
- `Service.AttachUserEventHub` wires the `platformevents.UserEventHub` that publishes only this instance's committed user top-up status hints; hints carry the payer account and fan out only to its current financial managers, the frontend re-reads Wallet, orders, or recharge history from it, and SSE is never a payment fact source.
- `Service.ReconcileDuePaymentOrders` is the River recovery seam and converges Checkout, Refund, and durable Dispute; `ListPaymentReconciliationAnomalies`, `ListAdminPaymentOrders`, `GetAdminPaymentOrder` are Admin read seams, HTTP/Admin presentation owns no reconciliation transition, and Admin detail returns only redacted Stripe identity, durable recovery facts, and a safe Dashboard URL.
- `Credits typed Commands` carry every Idea balance change caused by a payment outcome; Payments never writes the Ledger or balance projections directly.
- `credentials.Resolver` (`application/credentials`) is the sole Stripe credential read boundary: API-key / webhook-secret lookup and plaintext recovery for webhook intake/dispatch, checkout, refund, dispute, and reconciliation all funnel through it. The configuration service remains the only credential writer (encryption on publish).

The shared PostgreSQL repository owns `GetPaymentOrderPayerAccount`: Refund, Webhook, and Reconciliation read the same persisted Order payer for hints through this operation; aggregate-specific payer readers must not duplicate it.

## Invariants

- Purchases are non-refundable except where required by applicable law or expressly promised at purchase. Admin refunds support reviewed exceptions through the existing original-payment workflow; there is no general fourteen-day refund entitlement or time cutoff. Permanent Organization closure never automatically refunds or transfers Ideas to Personal, and does not remove mandatory rights or purchase promises.

- Stripe API Key and Webhook Secret are stored encrypted with platform secret material; they must never enter HTTP responses, logs, the Webhook Inbox, or Admin audit.
- Payments persists only the minimal Stripe IDs, amounts, currency, statuses, times, receipt URL, terms version, and restricted error summaries needed for convergence and audit; card data, full billing addresses, full raw payloads, plaintext Secrets, and internal stack traces are forbidden, and payment-fact retention is decided by a controlled ops process, never by manually deleting linked Ledger rows or unsettled states.
- Checkout enables neither Stripe Automatic Tax nor proactively requests or stores Customer addresses; minimal Billing data Stripe or a Payment Method collects for compliance is outside what the app can suppress.
- Webhooks must verify the signature with the raw body, the Webhook Secret of the retained Credential Generations, and a 5-minute tolerance before any business parsing or persistence; invalid or expired signatures never reach the Inbox.
- Stripe Event IDs are globally unique; redelivery stays idempotent, and signed-but-unknown events record only minimal metadata marked `ignored`.
- The Webhook Inbox stores no raw payload, only Event ID, type, object ID, livemode, Stripe created time, and receive/process status with timestamps.
- Configuration and Webhook Secrets are read from PostgreSQL at request time and take effect immediately, with no application-lifetime config cache; Payment Orders, Refunds, Disputes, Checkout shutdown, and Reconciliation must reach Stripe through the immutable Credential Generation referenced by the order, and switching the active generation neither scans old orders nor holds a global config lock during provider I/O.
- Before creating a Checkout, durably create or replay the Payment Order by `(billing_account_id, client_idempotency_key)` plus a canonical request hash binding the payer account and the purchase body; same key with a different request fails closed, cross-account key reuse never replays, and the Stripe Customer, Checkout Session, and provider identity all bind to that Order.
- Stripe Customers are reused per `(billing_account_id, stripe_account_id, mode)` namespace; test and live stay isolated, and API key rotation within one mode must not duplicate Customers.
- Every new Stripe Credential Generation must store an active, current-API-Key-verified `pmc_...`; Checkout creation passes that ID explicitly and never falls back to the Stripe Dashboard default.
- When Stripe deterministically refuses Customer or Checkout Session creation, the `creating` Order must move to `payment_failed` at once so the user can retry with a new Order; unknown-outcome failures (network break, rate limit, provider `5xx`, `idempotency_error`, incomplete response) keep the original Order and Stripe Idempotency Key.
- The Payment Order lifecycle uses `creating → checkout_open → async_payment_pending` for unfinished checkouts, `cancelled|expired|payment_failed` for unpaid terminal states, and `paid_pending_credit → credited` from confirmed payment to Ledger credit; a confirmed late paid fact may promote an unpaid terminal state to `paid_pending_credit`, no other terminal state regresses, and all transitions are database-constrained.
- One payer account with one Idea quantity may hold only one unpaid active Checkout; before reusing `checkout_open` or resuming `creating`, read or converge the Stripe canonical state and never return a completed or expired Checkout URL, and only after confirmed completion or expiry may the client rotate the Idempotency Key, while unknown-outcome provider failures keep the original key; Checkout create, continue, and abandon serialize per payer account without holding a database transaction across Stripe network calls, each account keeps at most 3 unpaid active Checkouts of different quantities, and `paid_pending_credit` is already a payment fact that consumes no unpaid slot.
- Only a paid Checkout Session with verified identity binding, learned from a signed Webhook or a server-side query, may credit; browser URLs, public tokens, and unpaid or failed Sessions never credit, the Stripe paid fact is first made durable alone as `paid_pending_credit`, and `purchase_credit` with `paid_pending_credit → credited` then commits atomically in one PostgreSQL transaction against the order's persisted payer account (no per-operator fallback), idempotent to replay and concurrency.
- Account recharge history returns only the authorized payer account's credited and user-abandoned order facts, with fully refunded credited orders projected as `refunded`, from the latest 12 calendar months in opaque-cursor pages (default limit 50, max 200 per the shared pagination standard); no payer PII, provider secrets, or internal Stripe metadata, and cursors are length-bounded before decoding.
- Dispute Webhooks trigger only a canonical Stripe Retrieve; open or lost Disputes create a reasoned Restriction, run a bounded `payment_dispute_debit`, and persist the unrecovered amount in one transaction on the order's fixed payer Billing Account under the fixed Payment Order to Wallet lock order, while `won` and `lost → won` restore exactly this Dispute's actual debit on the same payer account and release exactly its Restriction. Dispute checkout expiry targets the payer account's active Checkouts; member exits never move the obligation.
- Refund settlement converges on the order's fixed payer Billing Account at every phase (pending reservation, provider-result marking, succeeded `purchase_refund` / failed `release`); cumulative refunds plus open/lost disputes never exceed the order's paid facts, duplicate Stripe notifications replay without a second hold/debit, and insufficient Ideas follow the existing `ErrInsufficientCredits` anomaly policy without touching other accounts. Stripe I/O never holds a local transaction; the Admin refund reservation commits before the provider call and each settlement phase commits its funds commands, order/dispute status, and audit in one transaction.
- Admin refundable quantity reads the order's fixed payer Wallet; refund/dispute hints carry the payer account and fan out only to its current financial managers (operator-only fallback), and Admin re-reads the order detail after refund.
- User SSE is isolated by payer account and authorization: hints carry the payer account and reach only its current financial managers (operator-only fallback); delivery keeps heartbeat and cleanup over the connection lifetime; it notifies only `processing`/`credited`/`failed`/`refund_updated`/`dispute_updated` and never replaces Stripe or PostgreSQL as the payment fact source.
- The 5-minute River reconciliation only claims unconverged orders older than 2 minutes, at most 100 per batch; the claim lease outlives the worker timeout, token plus generation blocks stale workers from overwriting newer results, and multi-worker correctness never depends on queue concurrency.
- A `creating` Order persists the validated immutable return base URL and the whole-second expiry used for the first Stripe request; after restart or create timeout, replay with the original public order number and identical parameters under the same Stripe Idempotency Key instead of failing on the local timeout.
- `paid_pending_credit` retries only the atomic Credits credit, never re-queries or rewrites the Stripe paid fact; Stripe transient failures go to River retry, and deterministic config, permission, response, or identity-binding errors record a redacted operational failure and retry with delay to avoid hot loops.
- Orders still unconverged after 24 hours gain only a durable anomaly flag with no payment-state change; a later canonical terminal Stripe fact clears the anomaly.
- The Admin order read model strictly validates the canonical public order number, bounded user and status filters, and opaque cursors; it never returns public tokens, idempotency or request hashes, return base URLs, Secrets, or raw provider payloads.
- Fiat-to-Idea recharge uses the fixed 500~500,000 Idea schedule at 100 Ideas per USD and stays outside the Billing SKU Catalog, which prices only Idea-to-service consumption; user-visible prices are unchanged by this boundary.
- Payments changes no task-infrastructure ownership: River plus PostgreSQL stays the task queue and state fact source, NATS JetStream stays only the event layer.
